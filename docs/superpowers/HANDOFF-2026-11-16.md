Start a new context and say: "Read `docs/superpowers/HANDOFF-2026-11-16.md` and start with plan 1." Nothing from the redesign is implemented yet: only docs were written and edited.

## What was decided (all in `specs/2026-11-16-remote-playback-design.md`, approved by the user)

- **No saved session on the server any more.** The earlier recipe (seed, shuffle version, edit lists) was dropped as over-complex. A **live session** lives in server memory per account while someone listens: the queue as a real list (history, current, user queue, source part), the active device and the playback state. It is torn down after 10 minutes of inactivity (never while the active device is online and playing). Every device keeps a **local copy** of the last queue it saw; "Continue" resumes that local copy.
- **One active device plays; the others are controllers** over the existing SignalR hub (server relay). Events, not a position stream; controllers compute the moving position. Playback never needs the server.
- **Active device rules:** it keeps playing until the user changes device (picker) or it goes offline. Pressing play on a controller sends the command to the active device (the sound stays); with no live session the pressed device starts one. Reconnecting rule: a playing device that reconnects while another online device is active and playing is refused (it pauses and becomes a controller); otherwise it becomes active and its queue replaces the session's.
- **Queue:** any device can remove, play next (front of the user queue), add to queue (end of the user queue, plays before the rest of the source), and reorder (drag). The server owns the list and applies edits by `ItemID` in arrival order; the active device builds queues from its own synced library. Shuffle decides the order the source part is built in (random, no seed); toggling it regenerates only the source part. Setting `KeepQueuedItems` (synced, default false) keeps the user queue when a different source starts. A new upload joins a sorted Library queue only where the sort puts it after the current item. A deleted playing item finishes (ghost), then is dropped and never enters history.
- Per-playlist shuffle and repeat (null = global setting) is kept (backend plan 1, Task 4).

## Queue rules decided late (also in the plans; read these first)

- **Removing the playing song from the queue means skip.** A `Remove` of the current item (from any device, or racing an advance) makes the active device skip on at once; the song never enters history. A media file or playlist entry deleted from the library (`RemoveSourceItem`) is different: the playing song finishes, then is dropped (the "ghost" rule).
- **`Advance(Item?)` and `Previous(Item)` name the item now playing.** The device decides what comes next and reports it; the server accepts the named item even if a controller removed it a moment earlier (inserts it as `Current`), so there is never an error and arrival order does not matter. Naming the item also allows jumps ("skip two ahead"): songs skipped over in the same part are dropped by default (never enter history; history holds only songs that played or were left with Next, capped by `Remote:HistoryLimit`, cleared when a new source starts) or, with `KeepSkipped` true (a jump in the queue panel), moved to history in list order after the song left; jumping back with `KeepSkipped` puts the songs between at the front of the source part; a `JumpTo(item, keepSkipped)` command reaches the active device from a controller; the other part is untouched.
- **Next takes the user queue first, then the source part. Previous steps back one step in the normal queue:** the song left goes to the front of the **source part** whatever part it came from (a user-queue song stepped back over becomes an ordinary source-part song; accepted by the user).
- **Continue / "Play here"** is allowed whenever the device has a local copy, no device is active and nothing is playing (a live session may still exist after the active device dropped).
