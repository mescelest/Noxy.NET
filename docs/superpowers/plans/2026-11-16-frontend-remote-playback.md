# Frontend: The Live Queue and Remote Playback Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (the user wants this done natively, in the main session, not through subagents). Steps use checkbox (`- [ ]`) syntax for tracking. **Do not start before `2026-11-16-backend-remote-playback.md` and `2026-11-16-frontend-sync-settings-metadata-session.md` are done.** This plan runs before `2026-11-16-frontend-screens.md`, whose player bar, queue panel and Home read the services built here.

**Goal:** Rebuild the player on a real queue (history, current, user queue, source part) that any device can edit, make a device either the *active device* (it plays and reports) or a *controller* (it shows the active device's queue and state and sends it commands and edits), let the user move playback between devices, and keep a local copy of the queue on every device so playback and "Continue" never need the server.

**Architecture:** Everything lives in `Noxy.NET.MediaPlayer.Presentation` (no MAUI, Blazor or platform type) and the SQLite `Storage` project, tested with fakes and end to end against the real API. A `QueueService` owns this device's copy of the queue (the Domain's `LiveQueue`, shared with the server) and applies edits to it; a `RemotePlaybackService` owns the hub-facing state (devices, the live session's state, this device's role) and keeps the copy in step with the server's deltas; a `PlaybackReporterService` reports changes and claims the active role; the `PlayerService` stays the only thing that makes sound, now playing the queue's current item; a `PlaybackControlService` is what every screen calls and routes each action to the active device or to the local player.

**Tech Stack:** .NET 10, SignalR client, `Microsoft.Data.Sqlite`, xunit v3.

**Spec:** `docs/superpowers/specs/2026-11-16-remote-playback-design.md` (all sections); the hub contract is in `2026-11-16-backend-remote-playback.md` (the exact method, event and message names are the report of its Task 7).

## Global Constraints

- Work in `Presentation`, `Storage` and the two test projects (and `App/MauiProgram.cs` for registrations only). Target `net10.0`. No backend change. **No MAUI, Blazor or platform type in `Presentation` or `Storage`.** Windows first.
- Conventions of the earlier plans: one class per file named after it, no summary comment above a class, enums named `...Enum` in `Enums`, interfaces in `Interfaces/<same folder as the implementation>`, extensions in `Extensions`, `List` suffix, no `yield`, no magic strings (hub names are `nameof(MediaHubMethodEnum.X)` / `nameof(MediaHubEventEnum.X)`, times are `Constants`), `is null`, no `!`, method-syntax LINQ, "media" never "song", kind-first names (`serviceQueue`, `storeLocalQueue`), no helper classes, zero warnings, no commits, `git add -N` new files by name. Tests: unit in `Noxy.NET.Test.UnitTest/MediaPlayer/Presentation/`, store and end-to-end in the integration project, fakes in `Fakes`, helpers in `Fixtures`, `TestContext.Current.CancellationToken`, build then run the exe.
- **Playback never needs the server.** Every local action works with the hub disconnected and no session; being offline only disables the device picker and remote controls (with the reason "offline").
- **The queue** is the Domain's `LiveQueue` (`HistoryList`, `Current`, `UserQueueList`, `SourceList`, `QueueRevision`, `Source`), edited only through `QueueEdit`s applied by `LiveQueue.Apply`, the same code the server runs. A **source** is the Library (a sort, a direction, a search) or a playlist; the **source part** is the source in its play order, built by this device from its synced library and playlists. Ticked rows on a page are local and never a queue.
- **Shuffle decides the order the source part is built in.** Starting a source builds the whole source in the effective shuffle mode (`Off`: the source's order, `Random`, `SpreadArtists`: a random order made on this device, no seed is stored or sent), starting at the item pressed, and replaces the queue. Turning shuffle on or off regenerates only the source part from the current item (shuffled when on, in the source's order after the current item when off); the user queue is not touched. A shuffle's randomness comes from an injected `Random` so tests can fix it. Effective modes: the playing playlist's own `Shuffle`/`Repeat` when set, else the user's settings; a Library queue uses the global ones.
- **Repeat applies to the source part:** `No` stops when it runs out; `Once` appends the source once more (rebuilt, so a new shuffle), `Forever` appends it each time; the user queue plays once and is consumed.
- **`KeepQueuedItems`** (the synced setting): when a different source starts, `ReplaceSource` is sent with `KeepUserQueue` equal to it; the user queue then sits straight after the new current item, ahead of the new source part. Shuffle toggles and source changes never touch the user queue.
- **The source changes underneath** (a media file uploaded or deleted, a playlist edited; the device already syncs these): **the active device (or a device playing alone) applies `InsertSourceItem` / `RemoveSourceItem`**: an uploaded media file for a sorted Library queue goes where the sort puts it if that is after the current item (else it is not added), for a shuffled one at a random place after the current item; a deleted item that is playing **finishes first** (it is held as a *ghost* outside the queue), then is dropped from the queue and **never enters history** (so Previous goes to the item before it); a deleted playlist lets the current item finish and ends the source part. Controllers never send these.
- **Removing the current item from the queue means skip (decided 2026-11-16).** A `Remove` of the playing item (from any device, or racing a just-started advance) is pushed like any edit; the active device, seeing that its own current item was removed by a `Remove` delta, **skips at once** (`Advance` to the next item) and the removed item never enters history, so Previous skips it. This differs on purpose from a media file or entry deleted from the library or playlist (a `RemoveSourceItem`): that one **finishes playing first** (the ghost rule above). The server never answers an `Advance` or `Previous` with an error: both name the item now playing and the server accepts it even when a controller removed it a moment earlier.
- **Roles.** `PlaybackRoleEnum`: `Local` (no live session, or not connected: this device plays by itself), `Active` (this device is the active device), `Controller` (another device is active). Derived from the hub state, never stored.
- **Routing of every user action** (play, pause, seek, next, previous, volume, shuffle, repeat, start a Library or playlist source, queue edits, device change): in `Controller`, a command or an `EditQueue` goes to the server and **nothing changes locally until the pushed result arrives**; if the server answers `NoActiveDevice` the action runs locally instead and this device claims active; in `Active` and `Local` the action runs on the local player/queue first. Starting a source on a controller sends `PlayLibrary`/`PlayPlaylist` to the active device, which builds the queue and sends `ReplaceSource`.
- **The reconnect rule** (decided by the user): a device that is playing locally when it (re)connects sends `ClaimActive` with its state and its queue; refused: it pauses at once and becomes a controller; a device that is not playing only registers. A device that starts playing while connected and nobody is active claims active (this creates the session, with its own queue).
- **Deltas:** a pushed `QueueChanged` is applied only when its `QueueRevision` is exactly the local revision + 1; a lower or equal one is ignored (this device already applied it); a higher one means a gap and triggers `RequestSnapshot`. A snapshot replaces a controller's copy; on the active device it replaces the copy **except** that the active device's own `Current` and `HistoryList` win when the item still exists in the snapshot (the active device's pointer is the truth); when the snapshot shows the item the device is playing removed (`Current` null after a `Remove`), the device skips as above.
- **Reports are events, not a stream**: sent when the player's signature changes (playing or paused, the current item, a seek, the volume, the shuffle or repeat mode); never for a position change alone. `StateRevision` starts at 1 each time this device becomes active and rises by 1 per report. Controllers show the position as the reported position plus the time since it arrived while `IsPlaying`, never going backwards between reports.
- **Deferral on the controller:** `Seek` and `SetVolume` are sent once, `Constants.RemoteDeferMilliseconds` = 300 after the last change, through `IDelay`; everything else goes at once.
- **Volume** (decided by the user, revised 2026-11-16): volume is per device, not a synced setting. A controller's volume goes to the server and on to the active device, which applies it to its local player, stores it locally and reports it in its next state; other controllers show it from that report. A device that becomes active plays at its own stored volume.
- **The local copy:** every change to this device's queue, current item and position is saved to `ILocalQueueStore` (the position at most every `Constants.LocalQueueSaveSeconds` = 10 while playing, and on pause and exit). When the server says `SessionEnded` the device keeps its copy. "Continue" resumes the local copy.

## Review Focus

- **The reconnect and offline cases:** a refused device pauses in the same call that learns of the refusal and never plays alongside the winner; a device offline keeps playing, advancing its own queue, and on reconnecting while nobody plays becomes active and its queue replaces the session's; with the hub down every local action still works (Tasks 6, 8).
- **Edits racing:** two controllers editing at once, an edit naming an item the active device just played or removed, a delta arriving twice or out of order (ignored or resynced), and a snapshot never moving the active device's pointer backwards (Tasks 3, 5).
- **Shuffle and source changes:** toggling shuffle never replays what already played in this source part and never touches the user queue; an upload joins a sorted Library queue only if the sort places it after the current item; a deleted playing item finishes, then Previous skips it (Tasks 2, 3, 4).
- **Transfer:** the old device pauses and reports before the target starts, the target downloads missing files first and shows "waiting for a download", the target never starts twice, and a failed transfer leaves the old device playing and shows the failure (Task 7).
- **Seek and volume dragging** sends one command per drag, never one per step (Task 8).
- **A huge queue:** a Library queue of 20000 items builds, saves, sends and applies without blocking the UI thread for a visible stall (the build is a single pass; the local store write is one transaction) (Tasks 2, 3).
