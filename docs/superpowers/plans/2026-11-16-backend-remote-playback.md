# Backend: Remote Playback and the Live Queue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (the user wants this done natively, in the main session, not through subagents). Steps use checkbox (`- [ ]`) syntax for tracking. **Do not start before `2026-11-16-backend-session-removal-and-playlist-modes.md` is done** (it removes the saved session this plan replaces and moves `LibrarySortEnum` into the Domain).

**Goal:** Give each account one *live session* in server memory: the queue as a real list that any device can edit, the active device that plays, and the playback state; push every change to the account's other devices, forward commands to the active device, move playback between devices, and tear the session down after inactivity. Nothing about the session is stored.

**Architecture:** Two singleton services in `Application`, both pure in-memory logic with no hub: `DeviceRegistryService` (the online devices) and `LiveSessionService` (the session, its `LiveQueue`, the active-device rules and the idle timer). `MediaHub` gains client-to-server methods that call them; account-wide pushes are Mediator notifications turned into `Clients.User(...)` sends by API handlers, exactly like the existing pushes, and per-device sends (a command, a transfer request) go straight through `Clients.Client(connectionID)`. Queue edits are applied by item ID, in arrival order, by the server.

**Tech Stack:** .NET 10, ASP.NET Core SignalR, Mediator, xunit v3, `TimeProvider` / `FakeTimeProvider`.

**Spec:** `docs/superpowers/specs/2026-11-16-remote-playback-design.md` (all sections).

## Global Constraints

- Work in `Domain`, `Application`, `API` and the two test projects. No frontend change here. **Nothing is persisted**: no table, no migration. A server restart drops every device and session; devices register again.
- Conventions of the earlier plans: one class per file named after it, no summary comment above a class, enums named `...Enum` in `Enums`, interfaces in `Interfaces`, `List` suffix, no `yield`, no magic strings (hub method and event names are `nameof(MediaHubMethodEnum.X)` and `nameof(MediaHubEventEnum.X)`), `is null`, no `!`, method-syntax LINQ, "media" never "song", kind-first dependency names (`serviceLiveSession`), logic on the owning type or an extension (never a helper class), zero warnings, no commits, `git add -N` new files by name. Tests: unit in `Noxy.NET.Test.UnitTest/MediaPlayer/`, integration in `Noxy.NET.Test.IntegrationTest/MediaPlayer/`, fakes in `Fakes`, helpers in `Fixtures`, `TestContext.Current.CancellationToken`, build then run the exe.
- **Accounts are isolated.** Every operation is keyed by the user ID from the authenticated connection (`Context.UserIdentifier`, from `SubUserIdProvider`); no message names a user.
- **The queue is a list laid out as** `HistoryList` (played items, newest last, at most `HistoryLimit`), `Current` (an item or null), `UserQueueList`, `SourceList`. An **item** is `QueueItem(Guid ItemID, Guid MediaFileID)`; `ItemID` is unique inside a queue (a media file may appear twice under two item IDs). The server never builds a queue: it stores what devices send and applies edits.
- **Edits** (`QueueEditEnum`), applied by `ItemID`; an edit naming an item that is gone is a **no-op, not an error**; every applied edit increases `QueueRevision` by 1 and is pushed as a delta. From **any registered device:** `PlayNext(MediaFileID)` (front of `UserQueueList`, new `ItemID` made by the sender), `AddToQueue(MediaFileID)` (end of `UserQueueList`), `Remove(ItemID)` (from the user queue, the source part or history; when it names `Current` the item is dropped, `Current` becomes null and the item does **not** enter history: the active device sees this delta and skips on at once with an `Advance`: decided 2026-11-16, a removal from the queue means "I do not want this song"), `Move(ItemID, AfterItemID?)` (inside the upcoming part: `UserQueueList` and `SourceList`; moving a source item into the user queue makes it a user-queue item; `AfterItemID` null means the front of the user queue). **From the active device only:** `ReplaceSource(Source, ItemList, CurrentItemID, KeepUserQueue)` (the new source part from `ItemList` after `CurrentItemID`; history cleared; the user queue kept when `KeepUserQueue`, else cleared), `RegenerateSource(ItemList)` (replaces the source part, keeps history, current and user queue), `InsertSourceItem(Item, AfterItemID)`, `RemoveSourceItem(ItemID)` (the source changed underneath: unlike `Remove`, a playing item named here is left alone, the device lets it finish and the ghost rule of the client plan drops it afterwards), `Advance(Item?)` (the active device reports what it is now playing: `Current`, when not null, goes to history; the named `Item` becomes `Current`, **taken from wherever it is in `UserQueueList` or `SourceList`, and inserted as `Current` when it is in neither**; when it is further down than the front of its part (a jump such as "skip two ahead", or the device choosing a source song while the user queue is not empty) the items ahead of it **in the same part** are **dropped** (`KeepSkipped` false, the default: skipped and never heard, so they never enter history: history holds only songs that played or were left with Next) or, when the edit's `KeepSkipped` is true (the user jumped in the queue panel and wants to pass over them), **moved to history in list order right after the old `Current`**, so Previous steps back through them; the **other part is left untouched**, so the user queue still plays after it (a controller removed it in a race, but the device is already playing it, so the server accepts it and never answers with an error); a null `Item` means the end of the queue and leaves `Current` null), `Previous(Item)` (the reverse, one step back in the normal queue: `Current`, when not null, goes to the **front of `SourceList`** whatever part it came from (decided 2026-11-16: `Advance` takes `UserQueueList` first, so the user queue still plays before it); the named `Item` becomes `Current`, taken out of history when it is there, else inserted; when the named item is further back than the last history item, the history items after it are **dropped** by default or, with `KeepSkipped` true, **placed at the front of `SourceList` in order, ahead of the old `Current`**). Because both name the item, they give the same result whatever order they arrive in relative to other edits.
- **The reconnect rule (decided by the user).** A claim to become the active device is **refused only when another device of the account is online, is the active device and its last state is playing**; in every other case (no active device, the active device is offline or inside its grace period, or it is paused) it is accepted. A refused device must pause and become a controller (the client plan does that). An accepted claim makes the claimant active, stores its state, and **its queue replaces the session's queue** (the active device's own copy, possibly advanced offline, is the truth); with no live session it creates one.
- **Revision.** The active device numbers state reports with `StateRevision`; the registry keeps the highest accepted for the current active device and drops a report with a lower or equal number. When the active device changes the stored number is forgotten.
- **Configuration** (`ConfigRemote`, section `Remote`): `ActiveGraceSeconds` = 10, `TransferTimeoutSeconds` = 5, `IdleTeardownMinutes` = 10, `MaxDeviceCount` = 10, `MaxDeviceNameLength` = 50, `HistoryLimit` = 50, `MaxQueueLength` = 20000, `MaxHubMessageBytes` = 4194304 (the hub's `MaximumReceiveMessageSize`, raised from SignalR's 32 KB default so a queue of thousands of items can be sent).
- **Teardown.** A session ends after `IdleTeardownMinutes` of inactivity: nothing is playing (the state is paused, or the active device is gone past its grace period) **and** no command, edit or report arrived. The countdown never runs while the active device is online and playing, and any command, edit or report restarts it. Ending pushes `SessionEnded` (no payload) to the account's devices; the server keeps nothing.
- A command is never queued: with no active device it is answered `NoActiveDevice` at once. Commands are not acknowledged as done: the result is the next state report or queue delta.

## Review Focus

- **Concurrent edits from two devices, and an advance racing a removal:** two edits naming the same items arrive together and the result is one consistent list with a `QueueRevision` that rose by exactly the number of applied edits; an edit naming a gone item changes nothing and pushes nothing (Task 3).
- **Only the active device may change the source part, advance or report:** an edit or report of that kind from another device is rejected, nothing stored or pushed (Tasks 3, 5).
- **The reconnect rule and the claim's queue replacing the session's:** refused while another online device plays, accepted when it is paused, offline or in its grace period, two simultaneous claims leave exactly one active device (Task 4).
- **Teardown timing:** never while the active device is online and playing; starts when it pauses or goes offline past its grace period; any command, edit or report resets it; after it the account is told `SessionEnded` and a later claim creates a fresh session (Task 4).
- **Transfer going wrong:** to an offline or unknown device (refused), with an old device that never answers (the last state is used, advanced by the elapsed time if it was playing), a target that never claims (`TransferFailed`, old device stays active), and a second transfer during the first (Task 6).
- **Another account:** a device of account B never receives A's queue, state, commands or device list, and a message from a connection that is not a registered device is refused (Tasks 2, 5, 6, 7).

### Task 6: Commands and transfer

**Files:** modify `ILiveSessionService.cs`, `LiveSessionService.cs` (the transfer bookkeeping), `API/Hubs/MediaHub.cs`; tests `LiveSessionServiceTest.cs`, `MediaHubRemoteTest.cs`.

**Interfaces:**
